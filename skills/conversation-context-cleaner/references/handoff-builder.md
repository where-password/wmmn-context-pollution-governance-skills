# Pure Handoff Builder

This module converts resolved conversation state into database handoff suggestions.

Implementation: `scripts/conversation_cleaner/handoff_builder.py`

It is a pure function boundary:

- no file reads or writes;
- no CLI integration;
- no clean plan/apply integration;
- no network, LLM, embedding, environment-variable, clock, database, Milvus, or alias access;
- no canonical promotion or database write.

The builder reuses `MemoryObservation`, `StateTransition`, `MemoryWriteHandoffItem`, `PendingReviewItem`, and the idempotency contract from `handoff_contracts.py`.

## Entry point

`build_handoff(observations, transitions, workspace_id, project_id, domain_profile, profile_version, source_id)` returns a `HandoffBuildResult` containing:

- `write_items`: `MemoryWriteHandoffItem` suggestions;
- `pending_review_items`: review-only items that must not be auto-written;
- `skipped_observations`: observations intentionally excluded from this batch;
- `counts`: a read-only mapping-like `HandoffBuildCounts`.

`HandoffBuildCounts` supports both attribute and mapping access:

- `counts.write_items`
- `counts["write_items"]`

## Transition mapping

| Transition | Builder behavior |
|---|---|
| `new` | The current observation becomes one write item, unless superseded later in the same resolved chain. |
| `supersedes` | Only the new current observation becomes a write item. `supersedes_ref` points to the prior observation; `supersedes_id` remains null for the database adapter. |
| `conflict` | No write item for the conflicting observation; it becomes a pending-review item. |
| `needs_review` | No write item for the unresolved observation; it becomes a pending-review item. |
| `unchanged` | No duplicate write; the observation is recorded as skipped. |
| `historical_only` | No current-batch write; the observation is recorded as skipped. |

If an observation has no matching transition, the builder does not guess. It creates a `needs_review` pending item with the observation evidence.

If a `new` or intermediate `supersedes` observation is later superseded in the same resolved chain, the builder skips that historical intermediate. Only the final current state is proposed for writing.

## Write-item mapping

Each writable observation maps into a strict `MemoryWriteHandoffItem`:

- claim and scope identity: `claim_key`, `scope_key`;
- observable time: `observed_at`;
- transition: `transition_kind` and logical `supersedes_ref`;
- source: caller-supplied `source_id`, deterministic `source_unit_id`, and conversation-observation `source_scope`;
- memory semantics: `memory_type`, state-derived `subtype`, content, assertion source, verification state, effective interval, confidence;
- evidence: complete evidence set from the current observation and transition, including both ends for a supersede;
- database-only resolution fields: `supersedes_id=null`, `expected_version=null`;
- deterministic `operation_id`;
- deterministic `idempotency_key` generated by `materialize_idempotency_key()`.

The write item contains `declared_sensitivity` and `requested_visibility` only because they are database write-input declarations. It contains no authorization, ownership, canonical sensitivity/visibility, or storage-status fields.

## Chain safety

Every transition is validated before conversion:

- its target observation must exist;
- transition claim and scope must match the target observation;
- if it links a prior observation, both observations must share conversation, scope, and claim;
- cross-conversation, cross-scope, or cross-claim supersedes are rejected.

Different conversations and scopes therefore cannot be combined into one write item or one supersede.

## Evidence preservation

Evidence is merged by `evidence_id` and sorted deterministically. Conflicting payloads for the same evidence ID are rejected instead of silently choosing one.

For `supersedes`, the resulting write item contains both the replaced state's evidence and the current state's evidence.

## Ordering and idempotency

Output order is deterministic:

- write items by conversation, source sequence, observation ID, then idempotency key;
- pending-review items by conversation, source sequence, observation ID, then review ID;
- skipped observations by conversation, source sequence, observation ID, transition ID, and reason.

The builder does not mutate inputs. Repeating the same build yields the same dataclass values and serialized output, independent of input list ordering.

## Database boundary

This builder only prepares handoff suggestions. The database side must still:

1. authorize the write;
2. revalidate source and evidence;
3. independently review pending items;
4. resolve the logical `supersedes_ref` to a concrete database ID;
5. perform the actual supersede transaction;
6. enforce canonical sensitivity, visibility, ownership, versioning, and audit rules.

Until that approved database-side process completes, no canonical, Milvus, or alias state has changed.
